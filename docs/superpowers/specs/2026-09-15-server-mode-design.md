# Server Mode Design

## Goal

Let a team share the same `Block`/`Composition` library instead of each
person working against a private local ObjectBox file. Add a server mode
alongside the existing local mode — not a replacement — so a single desktop
install can still work fully offline.

## Scope

Add a new `textfoundry_server` binary that embeds the existing
`textfoundry_engine` (and, for AI actions, `textfoundry_ai`) and exposes an
HTTP API. Add an `IEngine` abstraction so the GUI can talk to either a local
in-process `Engine` or a remote server over HTTP without the viewmodels
knowing which. FTXUI CLI support, a dedicated admin TUI, and Postgres/
multi-tenant storage are explicitly deferred (see Out of Scope).

## Architecture

Local mode is unchanged: GUI/CLI construct `Engine`, wire it to
ObjectBox-backed `BlockRepository`/`CompositionRepository`, everything runs
in one process, exactly as today.

Server mode adds `textfoundry_server`, a long-running process that embeds the
same `textfoundry_engine` and the same ObjectBox repositories used locally
today. Its HTTP API is modeled on `Engine`'s public operations (PublishBlock,
UpdateBlock, RenderComposition, RewriteComposition, ...), not on raw
repository CRUD — all domain validation, rendering, and (in this scope) AI
actions execute server-side. The server is single-project, single-tenant: one
running instance serves one team's data. A second, independent team runs a
second instance with its own ObjectBox file; tenant isolation inside one
instance is not built.

## Client Abstraction

Today GUI viewmodels (e.g. `CompositionsViewModel`) hold a concrete
`tf::Engine` and call it in-process. Introduce `IEngine`, an interface
covering `Engine`'s current public surface, with two implementations:

- `Engine` — unchanged, local, in-process.
- `RemoteEngineClient` — new, each method issues an HTTP call to
  `textfoundry_server` and deserializes the response back into the same
  domain types (`Block`, `Composition`, `Result<T>`/`Error`).

Viewmodels and the composition root that constructs `Engine` today (GUI's
`SessionViewModel`) switch to depending on `IEngine`. `RemoteEngineClient`
wraps both HTTP failures (timeout, connection refused, non-2xx) and domain
errors into the same `Result<T>`/`Error` type `Engine` already returns, so
error handling in the GUI is identical in both modes.

## HTTP Framework and API Shape

Use [oat++](https://oatpp.io/) for `textfoundry_server`: zero-dependency,
~1MB, available via vcpkg, with built-in routing, request interceptors (used
for auth), DTO/JSON mapping, and Swagger/OpenAPI generation. oat++'s DTO
classes are the wire contract for the API and are mapped explicitly to/from
the engine's domain types (which use `reflectcpp`); the two serialization
systems are not shared, keeping the domain model free of wire-format
concerns.

## Authentication and Authorization

Auth is a new `ApiToken` entity (hash, label, `read_only` flag, encrypted
AI-provider key) stored in an ObjectBox store owned only by
`textfoundry_server` — not part of `textfoundry_engine`'s domain schema.
Requests carry a bearer token; an oat++ request interceptor validates it
against the token store.

`read_only` tokens may call read/render endpoints but not any write endpoint,
including AI-assisted preview actions (see below) — those cost real money
against an external provider even though they don't persist anything.

### Bootstrap

A fresh server has no `ApiToken` rows yet. The server reads an admin
credential from the `TF_ADMIN_TOKEN` environment variable at startup; that
credential authenticates only the admin API (token create/list/revoke), used
to create the first real `ApiToken`.

## AI-Assisted Actions

In scope for this server mode (not deferred). `textfoundry_ai`'s current
transport, `QtHttpTransport` (`src/textfoundry_ai/qt_http_transport.h`),
implements the existing `IHttpTransport` port using Qt — unsuitable for a
headless server binary. Add a second `IHttpTransport` implementation backed
by oat++'s own HTTP client, avoiding both a Qt dependency in the server and a
second HTTP client library.

AI-provider credentials move from per-client Qt keychain storage to
per-`ApiToken` storage on the server, so usage is attributable per token and
clients no longer need their own provider key. Qt's keychain integration
(`qtkeychain`) is not an option server-side: on Linux it calls
`org.freedesktop.secrets` over D-Bus, which requires a desktop secret-service
daemon that headless servers don't run. Instead, the AI key on each
`ApiToken` is encrypted at the application level (AES-GCM) before being
stored; the decryption master key is supplied via the `TF_MASTER_KEY`
environment variable at server startup and is never persisted.

## Concurrency Control

`Version` (major.minor) is generated by the engine when publishing — it is
not a token the client supplies — so two clients editing the same block from
the same base version don't collide on version numbers; the second publish
just silently ignores the first client's changes. Optimistic locking is
introduced explicitly: the publish request carries `based_on_version`.

Rather than an application-level mutex (global or per-id), add a new
repository/engine method, `UpdateBlockIfVersion(draft, expected_version,
bump)` (and the composition equivalent), whose ObjectBox implementation wraps
"read latest version → compare → write" in a single `obx::Transaction`.
ObjectBox already serializes all write transactions within a store — see
[ObjectBox transactions](https://docs.objectbox.io/transactions) — so wrapping
the check and the write in one transaction closes the check-then-act race
without any new locking primitive. A version mismatch aborts the transaction
and the endpoint returns `409 Conflict` with the current version in the body.

## Storage

The server reuses `textfoundry_engine`'s existing ObjectBox-backed
repositories unchanged — the same `database_scheme.fbs`/
`objectbox-model.json` compiled into `textfoundry_engine` serves both local
and server processes. Adding an entity to this shared schema is additive and
does not require migrating existing local databases.

ObjectBox Sync (the vendor's commercial sync product) and a Postgres backend
were both considered and rejected for this scope: Sync's licensing is
contact-sales and its model syncs local replicas rather than enforcing
version-based optimistic locking; Postgres would mean maintaining two
`IBlockRepository`/`ICompositionRepository` implementations for no scale need
this project currently has. Postgres remains the natural next step if a
real multi-tenant or horizontally-scaled deployment is ever needed.

## Error Handling

`Engine`'s existing `Result<T>`/`Error` maps to HTTP status: validation → 400,
not found → 404, version conflict → 409, missing/invalid/revoked token → 401,
unexpected → 500. Responses use one JSON error envelope
(`{"error": {"code", "message"}}`) via an oat++ DTO. `RemoteEngineClient`
performs the inverse mapping on the client.

## Testing

Follow the existing `tests/test_main.cc` doctest pattern. New server tests
start `textfoundry_server` in-process on an ephemeral port against an
in-memory ObjectBox store (the same fixture pattern the engine tests already
use) and exercise it with a real HTTP client: auth (valid/invalid/revoked
token, `read_only` restrictions), publish/read round-trips, the
`based_on_version` conflict path, and error-code mapping.
`RemoteEngineClient` is tested separately against the same in-process server.
`textfoundry_server` has no Qt dependency, so — unlike the GUI target — it
builds and its tests run in any CI job regardless of Qt availability.

## Deployment

Ship `textfoundry_server` as a Docker image (multi-stage: vcpkg build stage,
minimal runtime stage). Configuration and secrets (`TF_ADMIN_TOKEN`,
`TF_MASTER_KEY`, data path) are supplied via environment variables and a
mounted volume for the ObjectBox data file.

## Out of Scope / Deferred

- **FTXUI CLI server-mode support.** The GUI gets `IEngine`/
  `RemoteEngineClient` first; the CLI adopts the same pattern later once it's
  proven.
- **Dedicated admin TUI.** Token management (create/list/revoke, AI-key
  assignment) needs an interactive tool. The intended shape is an FTXUI TUI
  built on `terminal_ui_kit` (fetched via pinned-commit `FetchContent`)
  talking to a small admin-only HTTP API, separate from `IEngine`. This is
  explicitly **blocked** on finishing `terminal_ui_kit` first: that project
  currently has 17 open PRs from a benchmark exercise comparing coding-agent
  outputs on the same tasks (several features have 2-4 competing unmerged
  implementations). None of those PRs touch the `terminal_ui_kit` modules the
  admin TUI would actually need (basic components, virtual lists — both
  already merged to `main`), but the library as a whole needs that benchmark
  work resolved before depending on it. Until the admin TUI exists, the
  bootstrap `TF_ADMIN_TOKEN` path together with direct API calls (e.g. curl)
  is the only way to issue `ApiToken`s.
- **Multi-tenant / Postgres storage.** See Storage above.

## Delivery Tasks

1. **Extract `IEngine`.** Define an interface over `Engine`'s current public
   surface; make `Engine` implement it; update the GUI's `SessionViewModel`
   and viewmodels to depend on `IEngine` instead of the concrete class, with
   no behavior change in local mode.
2. **Add `UpdateBlockIfVersion`/`UpdateCompositionIfVersion`.** Extend
   `IBlockRepository`/`ICompositionRepository` and the ObjectBox
   implementations with the single-transaction check-and-write method;
   extend `Engine` to expose it.
3. **Add the non-Qt `IHttpTransport`.** Implement it on oat++'s HTTP client
   in `textfoundry_ai`, alongside the existing `QtHttpTransport`.
4. **Scaffold `textfoundry_server`.** New CMake target, vcpkg dependency on
   oat++, wiring to `textfoundry_engine`/`textfoundry_ai`, the separate
   `ApiToken` ObjectBox store, and the `TF_ADMIN_TOKEN`/`TF_MASTER_KEY`
   startup config.
5. **Implement the domain API.** Endpoints mirroring `Engine`'s block/
   composition/render/AI operations, DTO mapping, auth interceptor
   (including `read_only` enforcement), error-envelope mapping.
6. **Implement `RemoteEngineClient`.** HTTP-backed `IEngine` implementation
   plus client-side error mapping; wire it into the GUI as a selectable mode.
7. **Add server and client tests.** Per the Testing section above.
8. **Add the Docker image and deployment docs.** Multi-stage Dockerfile,
   environment-variable configuration, example `docker run`/compose
   invocation.

## Verification

`ctest --test-dir build-rel` covers the new `IBlockRepository`/
`ICompositionRepository` methods, the server's HTTP layer (auth, conflict,
error mapping), and `RemoteEngineClient`, alongside the existing engine
tests. Manually verify the GUI end-to-end against a locally run
`textfoundry_server` container: publish a block from one GUI instance,
confirm a second instance sees it, and confirm a stale `based_on_version`
publish is rejected with `409`.
